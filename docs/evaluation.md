# Phase 1 评估

离线自动测试用于验证流程与边界，不代表 LLM 质量。真实模型测试需要用户本地配置 API，未运行时明确记为「未验证」。

## 指标定义

- Recall@K：每条有答案问题检索到的相关来源数 / 标注相关来源总数，然后做宏平均。
- Hit Rate@K：至少命中一个标注来源的问题比例。
- MRR：第一个相关结果排名的倒数做平均。
- QA：人工核查答案关键词、实际含义、来源位置及是否支持回答。
- 无答案问题：单独统计拒答率，不放进有答案 Recall 分母。
- 延迟：检索、LLM、端到端分别记录；样本量小不能外推生产吞吐量。
- Token：只记录模型服务实际返回的 usage；缺失时为 null，不能填成 0 冒充没有消耗。
- Agent Tool Selection：本阶段未实现 Agent，因此不统计。

初始 Chunk 800 字符、Overlap 120、候选 12、Top-K 6、cosine 阈值 0.25。这些是起点，不是经过真实课程验证的最优值。字符数不是 Token 数。

## 本次实测

- 自动测试：23 项通过，包含实际格式解析、真实 Chroma、模拟 API HTTP 全链路、课程隔离、引用校验、上传限制、部分索引失败清理、重试及重启恢复。
- Edge 浏览器：真实上传 3 种格式，问题返回 3 个来源卡片；JavaScript 错误 0；390px 宽度无横向溢出。截图在本机 `data/screenshots`。
- 数据：3 份自编文件，14 个 Chunk，24 条问题。其中 8 条开发题、16 条保留题；20 条有答案、4 条无答案。
- 基线配置未按保留集调整。结果：文档级 Recall@6 **42.5%**，Hit Rate@6 **50%**，文档级 MRR **0.45**，此次请求错误率 **0%**。
- 这是哈希字词检索的演示基线，不是语义 Embedding 或 LLM QA 结果；不能声称答案准确率 50%。
- 模型 Token 用量为 null，真实 API 延迟、答案正确率、引用支持准确率均未验证。

详细逐题结果见 [evaluation-demo.json](evaluation-demo.json)。延迟记录同一 `/chat` 调用的 retrieval / total；额外的 `/search` 调用另记 `search_retrieval_ms`，避免将两次请求耗时混为一谈。

来源标注目前到文档级，故当前实现报告的是文档级 Recall / MRR，不是 Chunk 级指标。下一步应为真实课程标注具体页码与片段，并扩大问题集。

## 面试中如何如实介绍

可以说：「实现三格式课程资料 RAG 后端，使用真实数据库与索引验证隔离、引用和失败恢复，建立 24 条合成问题评估基线，明确区分演示检索与在线模型质量。」

不能说：「问答准确率达到 95%」「已经实现自主 Tool Calling Agent」「已服务大量学生」。本阶段没有这些证据。
