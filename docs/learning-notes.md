# 模块讲解与面试准备

## 1. API 骨架与配置

- 解决问题：提供稳定入口，把模型地址、密钥、路径等部署配置与源码分离。
- 为什么 FastAPI：函数就是接口，Pydantic 是可阅读的输入规则，还能自动生成接口文档。
- 替代：Flask 更轻；Django 带完整业务管理体系，本项目初期暂不需要。
- 优缺点：开发直接、类型清晰；仍需自己处理长任务、事务与模型错误，框架不会自动保证可靠性。
- 核心代码：`create_app(settings)` 是应用工厂。测试可以传入临时目录，不会触碰真实资料；`Settings` 启动时校验参数，错误配置尽早失败。
- 面试追问：为什么不把 API Key 写在代码中？为什么配置使用 `SecretStr`？同步函数和异步函数有什么区别？

## 学习顺序

先理解 Python 函数、类、类型注解、上下文管理器，再沿 ingestion 与 qa 两条流程读代码。不要从数据库内部或向量库内部开始读。

## 2. 数据库与上传

- 问题：文件、课程、来源、处理失败都必须持久化；不能只放进 Python 字典。
- 选择：SQLite 是单文件数据库，SQLAlchemy 让 Python 类对应数据库表。替代是 PostgreSQL，适合多用户、多写入进程。
- 事务：一次提交要么成功，要么回滚。但 SQLite 和 Chroma 之间没有共同事务，所以需要状态机、失败清理和可重建索引。
- 去重：对内容计算 SHA-256，同课程相同内容不能重复导入；不同课程可以分别导入。文件名不能当唯一标识。
- 面试追问：为什么查重之外仍需数据库唯一约束？崩溃发生在向量写入后、数据库提交前怎么办？

## 3. 文档解析

- 问题：不同文件格式必须变成统一的文本和位置结构，后续检索才能与格式解耦。
- 选择：成熟格式库负责读取，项目负责块结构和来源。替代是 OCR 或版面模型，可以处理扫描、复杂布局，但更重且存在识别误差。
- 限制：PDF 并不天然存储段落语义；复杂双栏、数学公式和图像需要后续增强。DOCX 页码受字体与排版影响，不能靠段落数量推算。
- 面试追问：如何保证引文页码？扫描 PDF 和文本 PDF 有何区别？表格跨块后如何保留含义？

## 4. Chunk 与 Embedding

- RAG 是检索增强生成：先从自己的资料中找证据，再让模型基于证据回答。资料更新不用重新训练大模型，还能提供来源。
- Chunk 是把长文档分成适合检索的片段。太长会混入不同主题；太短会丢条件和结论。Overlap 让相邻片段共享部分文字，减少断句损失，但增加存储与重复召回。
- Embedding 把文本变成数字向量。语义模型训练后可让含义相近的句子方向接近，查询和资料必须用同一个模型与版本。
- cosine similarity = 两向量点积 / 两向量长度之积，衡量方向接近程度。它不是答案正确概率。
- 演示哈希向量只把共享字词映射到同一维度，不能理解语义。不能把它的检索得分作为真实语义效果。
- 面试追问：为什么换 Embedding 模型必须重建索引？中文字符数与 Token 数是否一致？Overlap 应该用多少？答案需要通过自己的标注问题评估。

## 5. 检索与回答

- Top-K 是保留的候选数。K 大可能找全证据，也会引入噪声并增加模型输入成本。
- 向量检索擅长语义近似，BM25 擅长词项匹配，尤其是术语和编号。混合检索应先有纯向量基线，再用失败案例和评估证明收益。
- Rerank 是对少量已召回候选重新打分，常用更准确、但成本较高的模型。当前先不增加该依赖。
- 引用 ID 校验只能保证 ID 存在，不能证明每一句回答都被支持。证据不足、召回错误、Prompt 注入及模型先验都可能导致幻觉。
- 资料只作为数据传给模型。明确拒答规则、限制上下文、校验引用，并通过人工评估检查答案是否真正有依据。
- 面试追问：为什么相关性很高仍可能回答不了问题？「A* 时间复杂度」与「A* 评价函数」主题接近，但后者不是前者的证据。

## 6. 后续 Agent 的接口边界

Phase 1 的检索和问答服务可以在 Phase 2 封装为 `search_knowledge`、`locate_source` 工具。真正的 Agent 还需要模型选择工具、执行工具、读取 Observation 并判断下一步；本阶段没有这条循环。

未来必须设最大步数、工具参数 Schema、失败重试上限和课程权限范围。Memory、Planning 和 ReAct 会在实现时分别讲解，不提前引入框架隐藏逻辑。
